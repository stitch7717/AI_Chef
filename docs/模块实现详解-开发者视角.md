# AI 私厨 · 模块实现详解（开发者视角）

> 本文按面试讲解的方式组织：每个模块先讲"要解决什么问题、怎么设计"，再讲"数据结构和关键实现"，最后讲"怎么验证它是对的"。不写营销话术，只写真实代码里做了什么、为什么这么做、代价是什么。

## 零、先用三句话把项目讲清楚

1. **它是什么**：一个多用户的 AI 私厨应用——用户拍照或打字描述食材，Agent 优先检索本地菜谱库，未命中再联网搜索，给出带步骤和营养的菜谱，并把对话、库存、收藏都落库。
2. **技术形态**：FastAPI 单体（分层：router → service → repository → model）+ LangGraph Agent + PostgreSQL（业务表 + pgvector 向量）+ Vue 3 前端 + Nginx + Docker Compose。
3. **工程目标**：不是跑通 Demo，而是"能并发、能回归、能解释"——26 个后端用例、9 个压测场景、22 个已修复的真实缺陷。

**一句话架构**：请求进来先过 Nginx（反代 + 限流透传真实 IP），FastAPI 内部分层处理业务，AI 部分交给 LangGraph Agent（工具：本地 RAG、联网搜索），记忆与业务数据统一落在 PostgreSQL。

## 一、整体架构与分层

### 1.1 目录即分层

```
app/
├── api/v1/          路由层：只做参数校验、鉴权依赖、调用 service
├── services/        业务层：业务规则、事务边界
├── repositories/    数据访问层：SQL/ORM，一个聚合一个文件
├── models/          ORM 模型
├── schemas/         Pydantic 契约（入参/出参）
├── agents/          AI 域：embedding、RAG、Agent 装配
├── core/            配置、数据库、安全（JWT/bcrypt）
└── main.py          应用工厂 + lifespan 装配
```

**为什么这么分**：我在写 Java 时习惯了 Controller/Service/Mapper，这套分层的好处是"改一处不影响另一处"——比如把"收藏重复视为成功"这条规则从路由里挪到 service，路由完全不用动。代价是多一层文件跳转，小项目会显得啰嗦。

**职责边界举例**：路由层不写 SQL，仓储层不写业务判断。`get_owned_session` 这种"按 id + 当前用户查，查不到抛 404"的规则放在 api 层的公共函数里，因为它是"鉴权"的一部分而不是业务。

### 1.2 应用工厂与 lifespan

`main.py` 用 `create_app()` 工厂模式（对标 Spring 的 ApplicationContext）：中间件、异常处理器、路由挂载都在这里装配。重资源（Agent、连接池、embedding 模型）在 `lifespan` 里创建一次，放进 `app.state`：

```python
@asynccontextmanager
async def lifespan(app):
    agent, pool = await build_agent()     # 建 Agent + checkpointer 连接池
    app.state.agent = agent
    await backfill_embeddings()           # 给没有向量的菜谱补向量（幂等）
    yield
    await pool.close()
```

**取舍**：Agent 是重对象（模型客户端 + 工具 + 检查点存储），不能每个请求建一次；放 lifespan 里既保证只建一次，也保证进程退出时能优雅关闭连接池。`backfill_embeddings` 放启动阶段是因为它是幂等的、可并行的优化动作，不阻塞服务可用性判断。

## 二、数据层

### 2.1 模型设计的三个决策

**决策一：统一基类**。`Base + IdMixin(BigInteger 自增) + TimestampMixin(created_at/updated_at)`，避免每张表重复写主键和时间字段。

**决策二：菜谱食材用 Text 存 JSON 字符串，出参再转数组**。原因是这份数据是"只读展示 + 给模型看的上下文"，不需要按食材做 SQL JOIN 查询；用 JSONB 也可以，但当前没有查询需求，Text 更简单。代价是不能用 SQL 按食材筛选，需要的话得改成 JSONB + GIN 索引。

**决策三：向量列用 pgvector 的 `Vector(512)`**。维度必须与 embedding 模型严格一致——`BAAI/bge-small-zh-v1.5` 输出 512 维，写成 1536 会直接插入失败。这类"维度不匹配"是向量检索最常见的坑。

### 2.2 索引是业务正确性的一部分

| 索引 | 类型 | 作用 |
|---|---|---|
| `uq_user_recipe` | 唯一 | 同一用户同一菜谱只能收藏一次 |
| `uq_pantry_active_name` | 部分唯一（`WHERE consumed = false`） | 同一用户同一食材只能有一条"在库"记录，但允许历史消耗记录共存 |
| `recipes.embedding` | 向量（余弦） | 语义检索 |

**这里有个设计取舍值得讲**：库存为什么用"部分唯一索引"而不是"全表唯一 + 删除旧记录"？因为消耗记录要留痕（用户能看到"这周用完了哪些"），所以同名的消耗记录必须允许存在多条，唯一性只约束"未消耗"的那一条。部分索引正好表达这个语义。

### 2.3 异步会话与迁移

`core/db.py` 用 SQLAlchemy 2.0 async 引擎 + `async_session_factory`，每个请求一个 session（`get_db` 依赖负责关闭）。迁移用 Alembic，但本项目加了三处补丁：`env.py` 注入项目根路径（否则导不到 `app`）、补齐 `script.py.mako` 模板、迁移文件显式导入 `pgvector.sqlalchemy.Vector`（autogenerate 不认识自定义类型）。

## 三、认证与用户模块

### 3.1 注册/登录的真实实现

```python
# 注册：查重 → 哈希（线程池）→ 入库
if await user_repo.get_by_username(db, data.username):
    raise HTTPException(409, "用户名已被占用")
pwd_hash = await asyncio.to_thread(hash_password, data.password)

# 登录：校验（线程池）→ 签发 JWT
ok = user is not None and await asyncio.to_thread(verify_password, password, user.password_hash)
if not ok:
    raise HTTPException(401, "用户名或密码错误")
```

三个细节：

1. **`asyncio.to_thread` 不是可选项**。bcrypt 单次 200–400ms，直接放在 async 函数里会阻塞整个事件循环——压测时 8 并发注册耗时 7.2 秒、期间所有读接口一起变慢。移入线程池后降到 957ms。
2. **登录失败统一报"用户名或密码错误"**，不区分账号不存在与密码错误，避免账号枚举。
3. **注册和登录都限流 10 次/分钟**（按真实 IP），防撞库与刷号。

### 3.2 JWT 与鉴权依赖

token 用 HS256，payload 只放 `sub`（用户 id）与 `exp`（72 小时），不放昵称等可变信息（避免 token 里的数据过期）。`get_current_user` 依赖负责解析、验签、查库，返回 ORM 用户对象；所有需要登录的路由通过 `Depends(get_current_user)` 声明。

**为什么不用 Session**：多实例部署时 session 需要共享存储，而 JWT 无状态，横向扩容零成本；代价是无法主动踢人（除非维护黑名单），本项目通过短期有效期 + 前端清理来兜底。

## 四、会话与消息模块

### 4.1 数据结构

`chat_sessions`：`user_id`、`title`、`langgraph_thread_id`（UUID，Agent 记忆的隔离键）、`last_active_at`。
`chat_messages`：`session_id`、`role`（user/assistant）、`content`、`image_url`。

**关键点**：`langgraph_thread_id` 单独存一列，而不是直接用 session.id 作为 thread_id。原因是把"业务主键"和"Agent 记忆键"解耦——将来迁移记忆存储或重建会话时，不必动业务 id。

### 4.2 归属校验统一收口

```python
async def get_owned_session(session_id, user, db):
    session = await chat_repo.get(db, session_id, user.id)
    if session is None:
        raise HTTPException(404, "会话不存在")
    return session
```

所有会话相关接口（取消息、发消息、删除）都走这个函数。返回 404 而不是 403，是刻意的——403 等于告诉攻击者"这个 id 存在但不是你的"。

### 4.3 列表与首轮命名

会话列表按 `last_active_at desc` 返回，每次对话都会刷新该字段。首轮提问时如果标题还是"新对话"，用问题前 50 字自动命名——用户不用手动改名，列表也可读。

## 五、对话编排模块（项目最核心的部分）

### 5.1 为什么用 LangGraph 而不是手写循环

手写 ReAct 循环要自己处理：模型要调工具 → 执行 → 把结果塞回消息 → 再问模型 → 直到不调工具。LangGraph 的 `create_react_agent` 直接给了这个循环，并且带 **checkpointer**——把每一步消息写进 PostgreSQL，按 `thread_id` 隔离。

这意味着多轮对话的历史我**不需要手动拼**：传 `{"messages": [("user", 输入)]}` 加上同一个 thread_id，Agent 自己会加载之前的消息（包括工具调用与结果）。代价是记忆和业务消息表是两份数据（见 5.5 的双写）。

### 5.2 SSE 流式协议设计

事件只有四种：

| 事件 | 时机 | 数据 |
|---|---|---|
| `start` | 请求被接受 | session_id、thread |
| `token` | 模型每吐一段 | text |
| `done` | 全部结束并落库 | 两条消息 id |
| `error` | 生成失败 | 可读错误 |

**实现要点**：

- 返回 `StreamingResponse`，`media_type="text/event-stream"`；
- 响应头加 `X-Accel-Buffering: no`，Nginx 侧配 `proxy_buffering off`，否则流会被攒成一坨再一次性吐出；
- 生成器里用 try/except 包住整个流程，异常时推 `error` 事件而不是直接断开（前端能提示用户重试）。

### 5.3 只推模型正文：过滤工具消息

这是踩过的坑。`agent.astream(..., stream_mode="messages")` 会把链路上**所有**消息分片推出来，包括 `ToolMessage`——而工具消息的 content 就是工具的原始返回（Tavily 的 JSON、RAG 的结果字符串）。最初只判断了"content 非空"，结果用户看到的是 `{"score": 0.89, "raw_content": null ...}`。

修复后的过滤条件：

```python
if isinstance(chunk, ToolMessage) or getattr(chunk, "type", "") == "tool":
    continue
```

**为什么写成"排除工具消息"而不是"只允许 AIMessage"**：第一次就是这么写的，结果把单元测试里的假分片（非 AIMessage）也过滤了，测试直接失败。后者语义更贴近真实意图——"不要工具消息"，而不是"只要某一种类型"，对未来的消息类型也更宽容。

### 5.4 流结束后双写

流式过程中不落库（避免半截消息），结束后一次性写入两条：用户消息（原文 + 图片 URL）与助手消息（拼接后的完整回复）。`done` 事件把两个 id 返回给前端，前端据此刷新会话列表（标题可能已变）。

**代价**：如果用户在流式过程中关掉页面，后端仍会继续生成并落库（因为连接断开不一定能中断模型调用）。当前接受这个行为——用户回到会话能看到完整回复，比丢消息好。

### 5.5 双写的一致性

Agent 的记忆（checkpointer）与业务消息表是两套数据，我选择让它们"最终一致"：checkpointer 是权威记忆（决定下一轮上下文），业务表是展示与检索用。两者写入时机都是生成结束后，没有强一致事务——因为跨存储的强一致代价太高，而这里的偏差最多是"消息列表少了条"，不影响对话正确性。

## 六、Agent 装配与记忆存储

### 6.1 装配代码

```python
model = ChatOpenAI(model="deepseek-flash", temperature=0.7, timeout=120, ...)
web_search = TavilySearch(max_results=3, include_images=True, ...)
agent = create_react_agent(
    model=model, tools=[search_local_recipes, web_search],
    prompt=SYSTEM_PROMPT, checkpointer=checkpointer,
)
```

`temperature=0.7` 是有意的：菜谱生成需要一点表达变化，太低会变成模板，太高会乱编步骤。

### 6.2 系统提示词的约束方式

提示词只做三件事：规定工具优先级（先本地、后联网）、规定输出结构（菜名/食材/难度/步骤/营养）、规定语气（友好不冗长）。**不写"不要编造"这种空话**——防止乱答靠的是检索阈值和工具结果，而不是提示词。

### 6.3 checkpointer 的两个坑

`AsyncPostgresSaver` + `AsyncConnectionPool`：

- **连接串必须用 `127.0.0.1`**：Windows 下 `localhost` 可能先解析成 IPv6 `::1`，而 Docker 只绑了 IPv4，连接被静默拒绝，表现为"连接池一直重试"。
- **必须 `autocommit=True` + `prepare_threshold=0`**：`setup()` 内部有 `CREATE INDEX CONCURRENTLY`，不能跑在事务块里；`prepare_threshold=0` 走简单查询协议，避免服务端预编译语句在某些代理后失效。

## 七、本地菜谱 RAG 模块

### 7.1 向量化：离线批量 + 启动补漏

embedding 用 fastembed 跑本地模型（512 维，中文效果好，不需要 API key）。模型是全局懒加载单例——加载 1~2 秒，全进程只做一次。

菜谱向量不是入库时算的，而是**启动时补**：

```python
rows = await db.execute(select(Recipe).where(Recipe.embedding.is_(None)))
vecs = embed_texts([f"{r.name} {r.ingredients}" for r in rows])   # 批量，比逐条快
```

好处是导入菜谱（seed 脚本）与向量化解耦：导入脚本只管写业务字段，向量由服务启动时补齐，幂等且可重跑。

### 7.2 检索：阈值 + 混合重排

```sql
SELECT name, ingredients, 1 - (embedding <=> :qv) AS similarity
FROM recipes
WHERE embedding IS NOT NULL AND 1 - (embedding <=> :qv) >= 0.55
ORDER BY embedding <=> :qv
LIMIT :k
```

阈值 0.55 的作用不是"排序"，而是**判定本地是否命中**：低于阈值就返回空，Agent 转去联网搜索——避免硬套一个不相关的菜。

**混合重排是后加的**。菜谱从 10 道扩到 123 道后，"西红柿炒鸡蛋"的第一名变成了"西红柿鸡蛋汤"，因为纯向量对"炒/汤"不敏感。改进：

1. 向量召回扩大到 `top_k×3`（至少 8 条）；
2. 同义词归一（西红柿→番茄、马铃薯→土豆、尖椒→青椒）；
3. 词面分 = 0.6 × 字符二元组 Jaccard + 0.4 × 字符覆盖率；
4. 最终分 = 相似度 + 0.35 × 词面分，重排后截取 top_k。

**为什么不去调阈值凑测试**：阈值调低会让所有查询都"命中"，反而更差；混合检索解决的是"字面精确匹配"这个向量天然短板，是通用解法。

### 7.3 工具化的返回格式

工具不返回 JSON，而是返回一段人可读的短文本：

```
【番茄炒蛋】相似度0.73 | 难度:简单 | 食材:["番茄","鸡蛋"] | 营养:高蛋白…
```

原因：模型对结构化短文本的引用比嵌套 JSON 更稳，也不会浪费 token 在括号和引号上。

## 八、联网搜索模块

Tavily 配置 `max_results=3, include_images=True`，只取前 3 条（够模型综合，不浪费上下文）。工具结果**不会**直接出现在回答里——第 5.3 节的过滤器保证了这点；模型只拿它当上下文，输出自己的话。

提示词要求"本地未命中时再用联网搜索查权威做法，并注明来源"，来源以文字形式出现在回答里（不返回原始链接列表，避免前端渲染问题）。

## 九、库存模块

### 9.1 原子 upsert

```python
stmt = pg_insert(PantryItem).values(user_id=..., name=..., quantity=...).on_conflict_do_update(
    index_elements=["user_id", "name"],
    index_where=PantryItem.consumed.is_(False),
    set_={"quantity": ...},
)
```

**为什么要原子**：原来的"先查后改"在 30 并发下丢了 23 次更新（读-改-写竞态）。改成单条 SQL 后，数据库保证同一行的更新串行化，数量精确。

### 9.2 单位与重量体系（前端本地知识库）

后端只存 `quantity + unit` 两个字段，不做单位换算——**换算放在前端**，因为它只影响展示，且规则会频繁调整（不想为此改后端和迁移）。

前端 `data/ingredients.js` 维护 137 种食材：名称、平均单个重量（g）、默认单位、分类、图片。换算函数：

```js
toGrams(name, qty, unit) {
  if (unit === 'g') return qty
  if (unit === 'kg') return qty * 1000
  if (unit === '斤') return qty * 500
  if (unit === '毫升') return qty          // 密度≈1
  if (COUNT_UNITS.includes(unit)) {        // 个/条/片 按平均重量
    const m = matchIngredient(name)
    return m.avg ? qty * m.avg : null      // 无数据返回 null，页面不显示估算
  }
  return null
}
```

**单位为什么只保留 7 种**（个/g/kg/斤/毫升/条/片）："把、桶、袋、瓶"这类无法量化，写进去等于没写。用量词时必须给出平均重量（1 个苹果≈200g），否则不如直接记克数。

**舍入与降级**：`fmtWeight` 小于 1000g 显示 g，否则显示 kg；查不到平均重量时返回 null，页面干脆不显示"≈"，而不是显示一个错的数。

### 9.3 联想搜索

名称输入框用 `el-autocomplete`，候选来自本地 137 条知识库，匹配顺序：前缀命中 → 包含命中 → 分类命中（输入"调味"能列出调味品），最多 10 条。选中后自动带出默认单位——用户不需要知道"大米默认按克记"。

## 十、菜谱 / 收藏 / 反馈模块

**列表**：`limit` 用 `Query(50, ge=1, le=200)` 校验。这一点很重要——没有上限的分页等于给了一个拖库接口；超限返回 422 而不是静默截断，前端能立刻发现参数写错。

**搜索**：菜名 `ILIKE` 模糊匹配，不走向量（用户搜"番茄"期待字面结果，语义检索在这里反而添乱）。

**收藏**：靠唯一约束 + 捕获冲突转幂等。50 并发压测实测 0 个 500。

**反馈**：评分 1–5 + 是否真的做过（`cooked`），为后续推荐排序留数据。

## 十一、图片直传 OSS 模块

流程是"前端拿通行证 → 直传 → 回显 URL"，服务端不中转文件：

1. `GET /oss/presign?filename=x.jpg` → 返回 `uploadUrl` / `contentType` / `accessUrl`；
2. 前端 `PUT` 文件到 `uploadUrl`；
3. 聊天时把 `accessUrl` 作为 `image_url` 提交。

**签名算法（OSS V1 预签名）**：

```
StringToSign = "PUT\n" + Content-MD5 + "\n" + Content-Type + "\n" + Expires + "\n" + /{bucket}/{key}
Signature = base64(hmac-sha1(AccessKeySecret, StringToSign))
```

十几行标准库就能实现。**为什么不用官方 SDK**：SDK 依赖 pycryptodome 的原生 `.pyd`，在这台机器上被应用程序控制策略拦截（WinError 4551）。自己实现反而零原生依赖、跨平台稳定。

**安全细节**：接口必须登录（JWT），对象 key 加 `{user_id}/` 前缀（不同用户不会互相覆盖），扩展名走白名单映射 content-type（防止上传可执行文件）。

## 十二、内容资产管线（菜谱与食材图片）

这是"数据也是工程"的部分，三个脚本：

1. **菜谱导入**（`seed_recipes.py`）：按 name 幂等 upsert，重复执行只更新不新增；容器启动时自动跑。
2. **图片抓取**（`fetch_recipe_images.py`）：Tavily 搜图 → 结果里过滤掉社交平台防盗链域名（lookaside/instagram/fbsbx 等）→ 下载后解析 JPEG/PNG 头校验分辨率（≥400×300）与体积（>12KB）→ 落本地目录、DB 存相对路径。
3. **图片压缩**：Pillow 统一最长边 720px、JPEG q80、progressive，PNG 转 JPEG，同步改引用。总量 121MB → 17MB。

**为什么图片要本地托管**：外链有三重风险——源站被墙、防盗链、单张 5MB 拖慢首屏。本地化之后由自己的 Nginx 出图，配 30 天 immutable 缓存，首屏稳定在 40KB/张。前端还保留 `@error` 回退 emoji，保证永不破图。

## 十三、前端工程

### 13.1 三个基础设施

**路由守卫**：`beforeEach` 检查 localStorage 的 token，未登录去 `/login`，已登录访问 `/login` 回 `/chat`；末尾加 `:pathMatch(.*)*` 兜底，避免未知路径白屏。

**axios 拦截器**：请求自动带 `Authorization: Bearer`；响应 401 统一清 token 并跳登录页——不用每个页面各写一遍。

**SSE 客户端**：`EventSource` 不支持 POST 和自定义 header，所以用 `fetch` + `ReadableStream` 手写解析：按 `\n\n` 切块，逐行解析 `event:` 与 `data:`，回调 `onToken/onDone/onError`。

### 13.2 状态与体验

Pinia 的 auth store 持久化 token 与用户信息；页面首次加载从 localStorage 恢复，避免刷新掉登录。

**体验细节（都是自检时补的）**：列表加载骨架屏（不是空白也不是转圈）、移动端会话抽屉（原来侧栏在小屏被隐藏，等于删功能）、弹窗 92vw 自适应、全局 errorHandler 兜底（组件报错给 toast 而不是白屏）。

### 13.3 性能

Vite 分包：vue / element-plus 独立 chunk，业务代码更新不影响第三方缓存；Nginx 开 gzip（JS 体积降到约 1/3）、`/assets` 一年 immutable、图片目录 30 天缓存。

## 十四、部署与运维

- **镜像**：多阶段构建（Python 依赖层 + 运行层），模型缓存目录打进镜像，避免容器内联网下载。
- **编排**：Postgres / Redis / API / Web 四个服务，用 healthcheck + `depends_on: condition: service_healthy` 保证启动顺序（API 必须等数据库就绪，否则迁移失败）。
- **Nginx**：`/api` 反代（关缓冲支持 SSE、透传 X-Forwarded-For）、静态资源缓存、gzip。
- **配置外置**：数据库、JWT 密钥、OSS、Tavily 全部走环境变量，代码里不留密钥。
- **热部署通道**：镜像源不稳定时，`docker cp dist` 覆盖静态目录 + `nginx -s reload`，秒级生效。

## 十五、测试与质量保障

**单元/集成测试（26 个）**：pytest + `TestClient`，覆盖认证、会话隔离、SSE 协议、RAG 命中、收藏幂等、库存并发语义、菜谱分页边界。关键设计是**模块级 fixture**——连接池只建一次，所有用例在同一个事件循环里跑（asyncpg 连接绑定创建它的事件循环，跨循环复用必炸）。

**压测（9 个场景）**：5 个基线（入口/读/写/登录/多用户流程）+ 4 个业务级（尖峰 300 并发、写一致性、SSE 并发、30 分钟浸泡）。判定标准不是 QPS，而是"状态码正确 + 查库语义正确 + 内存不涨"。压测暴露了 bcrypt 阻塞、收藏竞态、库存丢失更新三个真实缺陷。

**回归纪律**：任何修复都必须重跑全量用例 + 同一压测场景。SSE 过滤器那次就是靠回归发现"修 A 坏 B"。

## 十六、如果重做，我会改什么

1. **前端按需引入 Element Plus**：现在全量引入首屏 JS gzip 约 300KB，按需可降到 ~100KB。
2. **图片上 CDN/OSS**：现在跟着应用容器走，发布时要重新打包静态资源。
3. **流式生成放任务队列**：长回答占用一个请求连接，极端并发下会挤占 worker；可以改成"提交任务 + 轮询/订阅结果"。
4. **补可观测性**：现在只有结构化日志，缺链路追踪与关键指标看板（首 token 延迟、RAG 命中率、工具调用失败率）。
5. **补前端 E2E**：目前前端靠人工回归，登录那次 `t.get` 崩溃就是"接口全绿、UI 全挂"的典型。
