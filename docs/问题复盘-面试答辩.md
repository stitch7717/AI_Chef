# AI 私厨项目开发问题复盘（面试答辩材料）

> 项目定位：面向个人消费者的 AI 私厨应用（拍照识食材 → 推荐菜谱 → 记住口味），按业务级标准建设：多用户、并发安全、可压测、可回归。
>
> 技术栈：FastAPI + LangGraph + DeepSeek（deepseek-flash）+ Tavily + pgvector + fastembed（BAAI/bge-small-zh-v1.5）+ PostgreSQL 16 + Vue 3 + Element Plus + Nginx + Docker Compose + 阿里云 OSS。
>
> 交付指标：后端自动化测试 26/26 通过；压测 5 个基线场景 + 4 个业务级场景全部达标（300 并发尖峰 0 错误，30 分钟浸泡 1800 请求 0 错误、内存平稳）；菜谱 123 道（全部配真实图片）；食材库 137 种（含平均重量与图片）。

## 二、详细复盘

### A. 环境与平台类

#### P1 服务无法启动：uvicorn.exe 被系统策略拦截

**现象**：命令行执行 `uvicorn app.main:app` 无任何输出直接退出；同期 `wsl.exe`、`pycryptodome` 的 `.pyd` 也可疑地加载失败。

**排查过程**：先用退出码确认不是语法错误；再逐个排除依赖、端口、环境变量；最后对比“同目录下 python 能跑但 exe 不能跑”，判断是二进制被拦截而非代码问题。系统层面确认存在应用控制策略（AppLocker/WDAC 类），禁止未签名可执行文件运行。

**根因**：安全策略只放行解释器，不放行第三方 `.exe` 与未签名扩展模块。

**解决**：改用解释器入口 `python -m uvicorn app.main:app`（不触发 exe 白名单），运行时依赖尽量选纯 Python 实现（例如 OSS 直传签名改为纯标准库 hmac-sha1 实现，避开 pycryptodome）。

**验证**：服务正常监听；同一命令在容器内与宿主机行为一致。

**面试话术**：这个问题的价值不在“绕过”，而在于我建立了“二分定位”习惯——先分辨是代码、依赖还是运行环境，再决定改代码还是改运行方式；同时尽量选纯 Python 依赖，减少对平台二进制的依赖。

---

#### P2 Windows 下异步事件循环不兼容

**现象**：Windows 上启动后，数据库/网络异步操作抛 `NotImplementedError`，或子进程相关功能不可用。

**根因**：Windows 默认 ProactorEventLoop 与 asyncpg 等库的 Selector 语义不兼容；而 uvicorn 在 Windows 分支里硬编码使用默认策略，没有给配置入口。

**解决**：编写 `run.py` 作为启动入口：显式 `asyncio.set_event_loop_policy(WindowsSelectorEventLoopPolicy())`，自建事件循环后 `asyncio.run(server.serve())`，绕开 uvicorn 的默认分支，同时保留 `--proxy-headers` 等生产参数。

**验证**：本地与服务容器行为一致；压测期间无事件循环相关异常。

---

#### P3 数据库迁移被安全软件中断

**现象**：psycopg 连接认证成功后立刻被 SIGTERM；同一时间 asyncpg 连接正常。

**排查**：用最小连接脚本对比两个驱动；抓取进程退出信号；确认是安全软件对特定驱动行为的误判（认证后即发信号），而非数据库侧问题（否则会有明确的 pg 错误码）。

**解决**：迁移脚本改用 asyncpg 直连执行（`scripts/apply_migration_a1.py`），执行后手动写入 Alembic 版本号保持版本一致；同时把迁移合并历史重复行的数据修复逻辑一并放进脚本，保证幂等。

**验证**：迁移后表结构、索引、版本号三项一致；重复执行无副作用。

**面试话术**：这类“环境杀进程”的问题不能靠猜，我用“两个驱动对比 + 信号确认”把范围收敛到单一变量，再选择替代路径，而不是去改安全策略。

---

#### P4 容器内模型下载失败

**现象**：镜像构建成功但启动时报模型下载超时；本地却正常。

**根因**：fastembed 首次使用需从 HuggingFace 拉取向量模型（约 91MB），容器网络受限且无代理。

**解决**：宿主机下载模型 → 拷贝进工程 `model_cache/` → 镜像内设置 `FASTEMBED_CACHE_DIR` 指向本地目录，实现离线可用。

**验证**：容器冷启动即可完成向量化；日志中不再出现下载请求。

---

#### P5 镜像源不稳定导致构建失败

**现象**：`docker compose build` 报 `failed to resolve source metadata ... EOF`，偶发、重试不稳定。

**解决**：生产仍以镜像构建为准；日常迭代采用“构建前端产物 → `docker cp` 覆盖容器静态目录 → `nginx -s reload`”的热部署路径，秒级生效、不依赖镜像源。

**面试话术**：这是典型的“构建链路可用性”问题。我的处理原则是：交付物用镜像保证可复现，日常迭代用热部署保证效率，两条路径互不干扰。

### B. 并发与数据库类（面试重点）

#### P6 bcrypt 阻塞事件循环

**现象**：8 个并发注册请求，总耗时 7.2 秒，且期间所有接口（包括不相关的读接口）全部变慢。

**排查**：压测脚本记录单请求延迟与整体 QPS；发现所有请求“几乎同时开始、几乎同时结束”，典型的串行化特征；再用一个纯读接口在注册期间测延迟，确认整条事件循环被卡住。

**根因**：bcrypt 是故意设计为慢的 CPU 密集算法（默认 12 轮）。FastAPI 的 async 路由运行在单线程事件循环里，同步调用 bcrypt 会把整个循环阻塞住，所有协程排队。

**解决**：`await asyncio.to_thread(bcrypt.hashpw, ...)` / `checkpw` 移入线程池，事件循环不再被占用。

**验证**：同样 8 并发注册从 7.2s 降到 957ms（约 7.5 倍），期间读接口延迟恢复正常。

**面试话术**：async 不等于免费并行。凡是 CPU 密集或同步阻塞库，都必须显式交出去（线程池/进程池/独立服务），否则并发越高、整体越慢。这是我做压测后才发现的问题，也是我认为“压测不是测 QPS，而是测系统在并发下的真实行为”的最好例证。

---

#### P7 收藏接口 50 并发出现 2 次 500

**现象**：同一用户 50 并发收藏同一菜谱，48 次 200、2 次 500；查库只有 1 行（唯一约束生效），但用户体验是“点了报错”。

**根因**：经典 check-then-act 竞态。两个请求同时通过“是否已收藏”的检查，随后都执行 INSERT，其中一个触发唯一约束 `uq_user_recipe` 抛异常，未被捕获 → 500。

**解决**：捕获 `IntegrityError`，按“已被收藏”处理，返回成功（幂等语义）；写操作不再依赖先查后写。

**验证**：50 并发 → 50×200、0×500，库中恰好 1 行。

**面试话术**：唯一约束不是麻烦，是最后一道防线。正确姿势是“让数据库兜底 + 应用层把冲突翻译成幂等结果”，而不是在应用层用查一次来保证唯一性。

---

#### P8 库存并发丢失更新

**现象**：30 并发对同一食材“加 1”，排查发现 23 次更新丢失（最终数量远小于预期），且没有报错。

**根因**：读-改-写三步非原子。两个请求读到相同旧值，分别 +1 后写回，后写覆盖先写；另外“同一食材只能有一条有效记录”仅靠应用层判断，并发下会插出重复行。

**解决**：两步走——
1. 写入改为单条原子 SQL：`INSERT ... ON CONFLICT (user_id, name) DO UPDATE SET quantity = ...`，把“查+改”合成一次数据库操作；
2. 增加部分唯一索引 `uq_pantry_active_name ON (user_id, name) WHERE consumed = false`，只约束“未消耗”的记录，允许历史消耗记录共存。

**验证**：30 并发后数量精确等于初始值 + 30；重复插入不再产生重复行。

**面试话术**：并发写正确性的三个层次：应用层加锁（差，单机有效）、数据库行锁/原子语句（好，跨实例有效）、唯一约束做最终兜底（必须有）。我做这个项目最大的收获是把“看起来对”改成“数据库层面可证明的对”。

---

#### P9 反向代理后限流失效

**现象**：压测时所有用户共享一个限流额度，正常用户被误伤；日志里客户端 IP 全是 Nginx 容器地址。

**根因**：slowapi 按 `request.client.host` 计数，反代后这个值恒为 Nginx 容器 IP。

**解决**：Nginx 追加 `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for`，uvicorn 启动加 `--proxy-headers --forwarded-allow-ips "*"`，让 ASGI 层正确还原真实 IP。

**验证**：不同来源 IP 额度独立；单 IP 超限返回 429。

**面试话术**：这是“链路中间件改变了应用假设”的典型案例。任何依赖客户端身份的功能（限流、审计、风控）都要在反代层显式传递真实来源。

---

#### P10 迁移工具链问题

**现象**：Alembic 在 Windows 下无法运行/生成空迁移/缺少模板文件。

**根因**：三个独立问题叠加——`env.py` 未把项目根目录加入 `sys.path`；`script.py.mako` 模板缺失导致无法生成脚本；`autogenerate` 不认识自定义 `Vector` 类型导致导入缺失。

**解决**：`env.py` 顶部注入路径；补全模板；在迁移文件模板中补齐 `from pgvector.sqlalchemy import Vector`；Windows 下同样使用 Selector 事件循环。

**验证**：`alembic upgrade head` 在本地与容器均通过，版本链连续。

### C. AI 工程类

#### P11 SSE 把工具原始 JSON 当成回答

**现象**：问“土豆烧牛肉怎么做”，前端流式输出的是一大段 `{"score": 0.89, "raw_content": null, "images": [...]}`——Tavily 的原始返回。

**排查**：LangGraph 的 `stream_mode="messages"` 会把链路上**所有**消息分片推出来，包括工具消息（ToolMessage）。原代码只判断“content 非空”，于是工具返回被当作模型正文。

**解决**：按消息类型过滤，明确排除 ToolMessage（含 `type == "tool"`）。第一次修复写成“只允许 AIMessage”，结果把测试替身（非 AIMessage 的假分片）也过滤了——测试立刻失败，说明过滤条件写窄了；改为“排除工具消息”的语义后，业务正确性与可测试性同时满足。

**验证**：同一问题重新提问，回答是结构化的菜谱（食材/步骤/营养），全文 0 处 JSON 泄漏；SSE 协议测试恢复通过。

**面试话术**：这个 bug 有两层价值。第一层是知道 `stream_mode="messages"` 的语义边界；第二层是“修复要匹配语义而不是匹配类型”——写“只放行 A”容易漏，写“排除 B”更贴近真实意图，也不容易误伤测试与未来新增的消息类型。

#### P12 菜谱扩容导致检索排序退化

**现象**：菜谱从 10 道扩到 123 道后，问“西红柿炒鸡蛋”返回的第一名变成“西红柿鸡蛋汤”，而正确答案“番茄炒蛋”排第二；单测因此失败。

**根因**：纯向量检索是语义相似度，对“炒/汤”“西红柿/番茄”这类字面与做法差异不敏感；扩容后相近候选变多，向量分差被压缩，语义相近但菜不对的结果上位。

**解决**：改为混合检索（Hybrid Retrieval）：
1. 向量召回扩大候选（top_k×3，至少 8 条）；
2. 查询与菜名做同义词归一（西红柿→番茄、马铃薯→土豆、尖椒→青椒等）；
3. 词面分 = 0.6 × 字符二元组 Jaccard + 0.4 × 字符覆盖率；
4. 最终得分 = 向量相似度 + 0.35 × 词面分，重排后截取 top_k。

**验证**：单测恢复（番茄炒蛋回到第一）；真实对话中“西红柿炒鸡蛋”命中本地菜谱且不再触发联网搜索；相似度阈值仍保留（0.55）用于判定“本地无命中”。

**面试话术**：向量检索解决“语义相近”，但解决不了“专有名词精确匹配”。工程上通常用混合检索 + 重排来兼顾召回与准确，这也是搜索/推荐系统的通用做法。我没有直接调阈值去“凑测试”，而是补了一层可解释的重排逻辑。

---

#### P13 LangGraph 记忆存储的连接问题

**现象**：Agent 初始化时连接池重试卡死；或建表时报事务相关错误。

**根因**：两个细节——Windows 下 `localhost` 可能优先解析为 IPv6 `::1`，而 Docker 端口只绑了 `127.0.0.1`，连接被静默拒绝；`AsyncPostgresSaver.setup()` 内部有 `CREATE INDEX CONCURRENTLY`，不能在事务块内执行。

**解决**：连接串强制 `127.0.0.1`；连接池参数 `autocommit=True`、`prepare_threshold=0`（走简单查询协议），并在应用 lifespan 中统一创建与释放。

**验证**：冷启动自动建表；多轮对话记忆按 thread_id 隔离；重启后历史可恢复。

### D. 前端与体验类

#### P14 登录、注册全部失败：`t.get is not a function`

**现象**：点登录无反应，控制台报 `t.get is not a function`；注册同样失败（实际上注册已成功，报错发生在注册后的“拉取用户信息”）。

**根因**：认证 store 里的 `fetchMe(api)` 把**业务接口对象**（只有 login/register/me 等封装，没有 `.get`）当成 axios 实例调用 `api.get(...)`。这个 bug 从第一版就存在，只是历史上所有测试账号都通过脚本/接口创建，从未有人在 UI 上登录过，所以一直没暴露。

**解决**：store 内部直接引用 `http` 实例调用 `/api/v1/auth/me`，调用方不再传参。

**验证**：UI 登录/注册均正常；接口层用 curl 复核返回 200 + token。

**面试话术**：这是“测试覆盖盲区”的典型案例——接口测试全绿，但用户真实路径（UI 登录）从未被自动化覆盖。它让我在后续补了前端关键路径的人工回归清单，也提醒我：接口正确 ≠ 产品可用。

---

#### P15 移动端无法切换会话

**现象**：手机宽度下会话侧栏被 CSS 隐藏，用户只能待在当前对话，不能新建或切换。

**解决**：移动端增加顶栏（菜单按钮 + 当前会话标题 + 新建按钮），会话列表放入左侧抽屉（el-drawer）；选中后自动关闭抽屉。

**验证**：≤768px 下可新建、切换、删除会话；桌面端布局不变。

**面试话术**：响应式不是“把元素藏起来”，而是“为小屏提供等价路径”。隐藏功能等于删功能。

---

#### P16 静态资源 121MB

**现象**：发现页首屏加载极慢，移动端流量消耗大；单张图片最大 5MB。

**根因**：抓图直接使用原图 URL 下载入库，无压缩、无尺寸上限。

**解决**：Pillow 统一处理：最长边 720px、JPEG quality 80、progressive；PNG 转 JPEG；同步更新数据库路径与前端食材库引用；Nginx 对图片设置 30 天 immutable 缓存，构建产物 365 天缓存，并开启 gzip。

**验证**：121MB → 17MB（-87%）；首屏图片单张约 40KB；重复访问命中缓存。

**面试话术**：图片是前端性能的第一杀手。原则是“按展示尺寸裁、按可接受质量压、用强缓存锁住”，而不是原图直出。

---

#### P17 菜谱只显示 120/123 道 + 后端分页无上限

**现象**：菜谱总数 123，前端只显示 120；同时接口 `?limit=9999` 也能返回 200。

**根因**：前端写死 `limit: 120`；后端 `limit` 未做范围校验，既可能拖垮数据库也让前端行为不可预期。

**解决**：后端改为 `Query(50, ge=1, le=200)`，超限返回 422；前端取 200 并支持后续分页扩展。

**验证**：列表返回 123 条；`limit=9999` 返回 422。

**面试话术**：分页参数是外部输入，必须在边界处校验。没有上限的分页等于给了一个“拖库”接口。

---

#### P18 图片源不可用（白图/破图）

**现象**：部分菜谱显示 emoji 兜底，部分图片 404。

**根因**：先是选用的 Wikimedia Commons 在国内被墙（容器与宿主机均超时）；换 Tavily 搜图后，返回结果里夹带 Facebook/Instagram 的 `lookaside` 防盗链地址，浏览器必然加载失败。

**解决**：建立三层处理——① 域名黑名单过滤（lookaside/instagram/fbsbx/tiktok 等）；② 下载后校验（JPEG/PNG 头解析、分辨率 ≥400×300、体积 >12KB，过滤图标与缩略图）；③ 全部下载到本地由自有 Nginx 托管，前端 `@error` 时回退 emoji，保证不出现破图。

**验证**：123 道菜 100% 有本地图片；抽查内容与菜名一致；单张约 40KB。

**面试话术**：外部数据源不可信，必须“过滤 + 校验 + 降级”三件套。尤其是图片这类非结构化资源，格式看似对但内容可能是广告图、缩略图、防盗链占位图。

---

#### P19 未知路由白屏 / 移动端弹窗溢出

**现象**：访问不存在路径得到空白页；手机上弹窗宽度 560px 超出屏幕。

**解决**：路由增加 catch-all 重定向到首页；全局媒体查询把弹窗/消息框宽度改为 92vw/88vw，抽屉内边距同步调整。

#### P20 联想下拉样式不生效

**现象**：食材联想能出结果，但图片尺寸、行高全部错乱。

**根因**：Element Plus 的弹层 teleport 到 `body`，组件 scoped 样式（含 `:deep`）作用域到不了弹层内部。

**解决**：样式提升到全局，用 `popper-class` 命名空间（`.ing-popper .ing-sug ...`）隔离，避免污染其他弹层。

**验证**：下拉条目图片 34px 圆角、两行文案正常；线上 CSS 已包含该类名。

### E. 测试与运维类

#### P21 测试跨事件循环复用连接池

**现象**：pytest 中偶发 `attached to a different loop`。

**根因**：asyncpg 连接绑定创建它的事件循环；测试用例各自 `asyncio.run()` 会新建循环，复用旧池即报错。

**解决**：连接池改为模块级 fixture，测试统一用 `with TestClient(app)` 在同一循环内执行；迁移脚本单独用 asyncpg 直连。

**验证**：26 个用例稳定通过，重复执行无偶发失败。

#### P22 限流提示中英混杂

**现象**：触发限流后用户看到 `请求过于频繁：10 per 1 minute`。

**解决**：异常处理器正则解析限额描述，转为“操作太频繁了，请稍后再试（每 1 分钟最多 10 次）”，无法解析时给通用中文提示。

**验证**：连续 11 次登录请求，第 10 次起 429，文案为纯中文。

## 三、面试高频追问与答题要点

**Q1：为什么选 FastAPI 而不是 Spring Boot？**
A：项目核心是 LLM 编排，Python 生态（LangChain/LangGraph、向量模型）是决定因素；FastAPI 原生异步、Pydantic 校验、OpenAPI 文档齐全，适合快速迭代。代价是缺乏 Spring 那样的全家桶，所以我在工程上手工补齐了分层（router/service/repository）、依赖注入、迁移、限流、测试，思路对标 Spring。

**Q2：怎么保证并发安全？举两个真实例子。**
A：收藏用“唯一约束 + 捕获冲突转幂等”；库存用“原子 upsert + 部分唯一索引”。核心原则是把正确性下沉到数据库，而不是靠应用层先查后写。压测验证：50 并发收藏 0 个 500；30 并发加库存数量零丢失。

**Q3：RAG 为什么用 pgvector 而不是 FAISS？**
A：多用户、多实例场景下，向量要和业务数据一起做权限过滤与事务更新，放数据库里最省事；FAISS 是本地索引文件，多进程/重启一致性维护成本高。规模上来后可以再引入专用向量库。

**Q4：怎么判断“达到业务级”？**
A：不看单接口 QPS，看四类硬指标——① 尖峰：300 并发瞬时打读接口，错误率 0；② 流式：SSE 多路并发不串流不截断；③ 一致性：压完**查库**断言业务语义（不是只看状态码）；④ 浸泡：30 分钟持续混合负载，内存不增长（311.8→311.6MB）。四项都过才算业务级。

**Q5：你遇到过最难排查的 bug？**
A：SSE 泄漏工具 JSON。因为它“功能看起来正常”（有输出、能结束），只是内容是错的；要从框架的流式语义入手，才知道 `messages` 模式会把工具消息一起推出来。修复后又因为过滤条件写得太窄导致测试失败，第二次才收敛到正确语义。

**Q6：多用户数据隔离怎么做的？**
A：双层——接口层每个查询都带 `user_id` 条件；资源访问统一走“按 id + 当前用户查询”的仓储方法，查不到即 404（不泄露资源是否存在）。实测：B 用户读写 A 的会话均 404，库存列表互不可见。

**Q7：如果流量涨 10 倍，你先改哪里？**
A：① 无状态 API 横向扩副本（记忆在 PG，不在进程内）；② 向量检索加索引与缓存，热点菜谱走 Redis；③ 图片上 CDN；④ 限流按真实 IP 分桶并调阈值；⑤ 把 bcrypt 之类 CPU 密集操作进一步隔离到独立线程池/服务。压测数据支撑：数据库读 163 QPS、写 142 QPS 是当前单实例瓶颈点。

**Q8：项目还有什么不足？**
A：① 前端全量引入 Element Plus，首屏 JS gzip 约 300KB，可按需引入降到 ~100KB；② 图片托管在应用容器，生产应上 CDN/OSS；③ 缺前端 E2E 自动化（目前是接口级 26 个用例 + 人工回归）；④ 无管理后台（用户/菜谱运营目前靠脚本）。

**Q9：怎么保证 AI 不乱答？**
A：三层约束——系统提示词规定输出结构（菜名/食材/难度/步骤/营养）；工具调用优先本地库，未命中才联网并要求注明来源；检索侧用阈值 0.55 判定“本地无命中”，避免强行套用不相关菜谱。

**Q10：这个项目你最大的收获？**
A：从“能跑”到“可证明能跑”。具体是三个习惯：改动前先量化（压测/单测），修复要匹配语义而不是匹配现象，所有外部输入（分页、图片、第三方返回）都要做边界校验与降级。

## 五、复盘方法论（可迁移）

1. **先分类再动手**：代码 / 依赖 / 环境 / 数据，四类问题的排查路径完全不同，混在一起只会浪费时间。
2. **量化优先于感觉**：加日志、加计时、加压测，用数字证明“慢”和“丢”，否则修完不知道有没有修好。
3. **修复要匹配语义**：不是把报错压掉，而是让行为符合业务语义（收藏重复=成功、并发加库存=累加）。
4. **正确性下沉**：能用数据库约束/原子语句解决的，不要用应用层逻辑“保证”。
5. **外部输入一律不可信**：分页、第三方 JSON、图片、用户输入，全部校验 + 降级。
6. **每次修复都要有回归**：改完跑全量测试与同一压测场景，避免“修 A 坏 B”（本项目的 SSE 过滤器就是这样被抓出来的）。
